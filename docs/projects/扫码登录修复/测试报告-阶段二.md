## 三、重点核查结论（逐条）

### 3.1 加密实现正确性 —— ✅ 通过

| 要点 | 结论 | 依据 |
|---|---|---|
| PKCS7 填充/去填充 | ✅ | `kg_crypto.dart:177-183`（pad=block-(len%16)，整除时为 16）、`:185-195`（逐字节校验 pad、越界/空判非法）；非法数据抛 `FormatException`（`:76-91`） |
| 两套 AES 密钥派生 | ✅ | `md5KeyIv`（`kg_crypto.dart:50-53`：AESKey=md5(key) 32 字符 ASCII→AES-256、IV=后 16 位）；`webKeyIv`（`:56-57`：16 位 key 同时作 key/IV→AES-128）。Node/OpenSSL 独立复算两套固定向量均一致（4.2） |
| AES-CBC 分块加密/解密 | ✅ | `:60-72`、`:76-91`，用 pointycastle `CBCBlockCipher(AESEngine)`，逐块处理；Node 解密密文可还原明文（4.2） |
| textbook RSA（零左填充 raw modPow） | ✅ | `:95-111`：明文 `setRange(keyLen-len, keyLen)` 零左填充 → `BigInt.modPow(e,n)` → `padLeft(256).toLowerCase()`；Node `BigInt` 独立计算两把公钥的密文均一致（4.2） |
| RSA 公钥/PEM 解析 | ✅ | `:114-137` 手写 DER TLV 解析 SubjectPublicKeyInfo → RSAPublicKey → modulus（去掉 ASN.1 符号 0x00）；Node `createPublicKey(pem).export(jwk)` 得到的模数与之逐字符一致（4.2） |
| 官网 JS 内置公钥（第二把） | ✅ | `webPublicModulusHex`（`:30-34`）与 PEM 公钥为两把不同 1024 bit 密钥（单测 `test/kugou_login_crypto_test.dart:112-117`；QA Node 复核 bits=1024、两者不同） |
| hex 大小写/工具 | ✅ | `toHex` 小写（`:143-144`）、`md5Hex` 小写（`:140-141`）、RSA 输出小写；kugou 请求签名仍 MD5 大写（`kugou_api.dart:61-64`，与官方 `getInterFaceKguser` 一致） |
| 单测向量是否可信 | ✅（经独立复核） | 单测 17 项见 5.2；固定向量由 QA 用 Node/OpenSSL 独立复算全部一致（4.2），**不是只靠"测试通过"**。但注意：向量只证明"实现 = 标准算法"，**不能证明服务端期望的一定是这两套派生约定**（见第七节风险 R1） |

### 3.3 一次性 token / 授权 code 风险 —— ✅ 通过（附残留风险）

| 检查 | 结论 | 依据 |
|---|---|---|
| 酷狗三候选是否重复消费同一 token | ⚠️ 有风险但可控 | `_loginByToken` 依次尝试 3 套约定（`kugou_api.dart:488-516`），**仅在上一次返回 `status != 1` 或抛异常时才试下一套**（`:556-561`），首次成功即 `return`（`:585-589`）。若 token 为一次性且首次请求在服务端已消费但响应丢失，后续候选必然失败 → 只降级为 userid+token 会话，不崩溃；风险已由"降级 + lastError"兜底，详见第七节 R3 |
| QQ 授权 code 是否被重复请求 authorize 消耗 | ✅ 未重复请求 authorize | authorize 成功后 `break`（`qq_api.dart:654-659`），不会再请求授权页；POST 405/400 才降级 GET（`:640-653`），此时尚未产生 code，安全 |
| QQ QQLogin 跨 base 重试是否复用同一 code | ⚠️ 符合任务口径 | 同一 code 依次请求 `musicu.fcg`→`u6.y.qq.com`→`musics.fcg`（`qq_api.dart:661-694`），仅重试"QQLogin 这最后一步"（任务允许"只重试网络层"）；若首次在服务端已消费而响应丢失，后续必然失败 → 返回 null + lastError，属可接受降级。业务失败（如假 code 的 code=1000）也会换 base 重试，属"无意义但无害" |
| 快速假参数实测端点行为 | ✅ | 见 4.1：check_sig 302、authorize 302 到授权页（无 code）、QQLogin 主/备1 返回业务 code=1000、备2 musics.fcg 外层 code=2000（需 zzc sign）——端点全部可达，**成功路径未验证** |
| 超时后是否继续消耗 | ⚠️ 有残留 | 见 6.2-N2：kugou 超时标记只在响应返回后检查，超时后循环仍可能发出下一候选请求；QQ `.timeout` 只包返回值，底层兑换超时后仍可能继续请求并晚到写 `_lastError`。均不写坏登录态（`kugou_api.dart:556,594`；`qq_api.dart` 兑换方法不写 `_loginCookies`） |

## 七、风险与未覆盖（重要）

| # | 风险 | 说明 |
|---|---|---|
| R1 | **未真机扫码，兑换链路仍未端到端验证** | 所有验证都止步于"端点可达 + 参数结构被接受"：酷狗 `status==1` 成功响应、`secu_params` 解密、QQ 真实 p_skey/authorize code/QQLogin 成功返回 musicid/musickey 均未真实执行。测试向量证明算法正确，但**不能证明服务端期望的密钥派生恰是这两套**（三候选即为此兜底） |

| R5 | UI 未实机验证 | 弹窗（QQ 图片二维码/酷狗图片二维码）、设置页提示、登录成功后 Hive 持久化均未在真实 GUI 点击验证 |

| R7 | 失败降级"提示"未落地（F1） | 用户会看到"登录成功"但实际只有 userid+token，VIP 可能不可用 |
| R8 | 酷狗登录 cookie 未消费（F2） | 补全的登录态不参与播放请求，VIP 权益不会因此生效 |
