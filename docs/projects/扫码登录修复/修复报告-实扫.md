## 二、根因定位与证据

### 2.1 网易云：接口没坏，客户端把响应丢了（已确证）

**在线实测（2026-11-09 01:0x，本机直连，`dart run tool/check_netease_qr.dart`）**：

```
=== 1) NeteaseApi.createQrLogin() ===
[JXMusic][网易云登录] 取码 HTTP=200 code=200 unikey=d3a9…f8b3(len=36)
[create] qrUrl=https://music.163.com/login?codekey=d3a9…(len=36) key=d3a9…(len=36) lastError=-
=== 2) NeteaseApi.pollQrLogin()（无人扫码，应保持等待态）===
[JXMusic][网易云登录] 轮询 HTTP=200 code=801 message=等待扫码
[poll1] session=null(等待) lastError=-
...（poll2/poll3 同）
=== 3) 原始 client/login 响应（证明端点可达与 code 语义）===
[raw] HTTP=200 body={"code":801,"message":"等待扫码"} set-cookie-names=[NMTID]
结果：PASS（取码成功、轮询为 801 等待态、client/login 端点可达）
```

独立第二次探测（PowerShell `Invoke-WebRequest`，与 Dart 实现无关）：

```
POST https://music.163.com/api/login/qrcode/unikey        → 200 {"code":200,"unikey":"40bb…"}
POST https://music.163.com/api/login/qrcode/client/login  → 200 {"code":801,"message":"等待扫码"}
```

结论：`unikey` 与 `client/login` 端点均可用，**"扫码确认后无反应"不是接口下线**。旧代码的 4 个具体缺陷（`lib/services/api/netease_api.dart` 修改前 365-394 行）：

1. **强转**：`final code = resp.data['code'] as int?;` —— 服务端若返回字符串 `"803"`，Dart 抛 `TypeError`，被设置页 `_poll` 的 `catch (_) {}` 吞掉，表现为"永远等待"。
2. **静默**：`pollQrLogin` 无 try/catch、`lastError` 恒为 null，任何网络/解析异常都不可见。
3. **803 只读响应体**：`resp.data['cookie'] ?? resp.data['token']`；但本轮实测等待态 801 的 Set-Cookie 只有 `NMTID`，官方 2026 文档（MiniPlayer `API_ANALYSIS.md` 2026-04：803 从 **Set-Cookie** 提取 MUSIC_U）与独立实现（Live-streaming `test_netease_qr_login.py`：803 响应体只有 `{code, message}`，`MUSIC_U` 在响应头）都指向同一结论：**旧代码即使拿到 803 也只能得到空 cookie 会话** → 对应现象 C（"提示成功但实际未登录/重启掉线"）。
4. **状态码无语义**：800（过期）/802（待确认）与 801（等待）同样返回 null，过期后也永远等待。

### 2.2 QQ：参数与参考实现一致，失败发生在 check_sig 的响应解读/尝试策略（部分确证）

**与参考实现逐字段比对（`L-1124/QQMusicApi` main 分支 `qqmusic_api/modules/login.py::_authorize_qq_qr`，2026 现存维护）**：

- `_checkSigParams()` 的 18 个参数（uin/pttype=1/service=ptqrlogin/nodirect=0/ptsigx/s_url=login_jump/ptlang=2052/ptredirect=100/aid=716027609/daid=383/j_later=0/low_login_hour=0/regmaster=0/pt_login_type=3/pt_aid=0/pt_aaid=16/pt_light=0/pt_3rd_aid=100497308）**与参考实现逐字段一致**；域名同为 `https://ssl.ptlogin2.graph.qq.com/check_sig`。
- 参考实现的关键差异：
  1. **不跟随重定向**（`allow_redirects=False`），直接读**首个响应**（成功路径是 302）的 Set-Cookie 取 `p_skey`；
  2. check_sig 请求**不带 Cookie**（`cookies={}`）；
  3. 该库的传输层 `AsyncSession(..., allow_incoming_cookies=False)`，即响应 cookie 不会被会话自动保存——说明 p_skey 必须从**该次响应头**显式读取。
- 外部证据（l-1124/QQMusicApi **issue #98**，2024-12）：真实扫码后的报错栈里 check_sig 成功返回
  `302 Found ... Redirect location: 'https://graph.qq.com/oauth2.0/login_jump'`，不是错误页。
  而旧实现 2026-11-09 实扫观测到的是"`HTTP 200, location=空, 已跳转 1 次`"——即旧实现跟随后落到一个 200 页面（与 QA 假参数探测 `check_sig → 302 location=https://www.qq.com` 同型），**说明该次 check_sig 并未走到成功分支**。
- 旧实现的策略缺陷（`qq_api.dart` 修改前 650-708 行）：
  1. 首个响应无 `p_skey` 时只"跟随 3 跳"，**没有再次尝试**（不带 Cookie / 带 qrsig / 用服务端 URL 三种形态都没有）；
  2. ptuiCB 返回的 `redirectUrl` 是服务端给的**完整 check_sig URL（含签名参数）**，旧实现只从中正则抠 `uin`/`ptsigx` 后**丢弃 URL 本身**，重建参数请求；
  3. 日志只输出"lastError 一句话"，没有每跳 status/location/Set-Cookie 名称/p_skey 判定，**无法区分**"服务端没下发 p_skey"与"客户端解析漏了"。

**待实扫 logcat 定案的 3 种可能**（新代码已全部覆盖尝试并在日志留证）：
- a) 服务端在新版下确实不下发 `p_skey`（则日志会显示三次尝试的 set-cookie 名称中都没有 p_skey）；
- b) 请求形态问题（Cookie/URL）→ 新代码第 2/3 级尝试会命中并成功；
- c) `uin/ptsigx` 已失效或被重复消费 → 日志会显示 3 次尝试均 302→www.qq.com 类错误页。

### 2.3 现象 C（登录成功但未登录 / 重启掉线）

- 网易云：2.1 第 3 点已确证（空 cookie 会话）。新代码在 803 时同时收集**响应体 cookie**与**响应头 Set-Cookie**，并要求 `MUSIC_U`（或 `MUSIC_A`）存在，缺失时**不返回会话**而是写 `lastError`。
- Hive 持久化链路本身（`lib/providers.dart` 33-68 行：`musicHubProvider` 构造时 `restoreSession(_loadAccount(...))`；`AccountNotifier.login` 写 Hive；`settings_page._showQrLogin` 写 Hive + 同步客户端）静态检查未见问题；本轮在设置页加了"登录态已写入"日志（`settings_page.dart:385`），实扫成功后会打印 `platform/nickname/cookies 数量`，再重启 App 复核是否仍显示已登录（见第七节未验证项）。
