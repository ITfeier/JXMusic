## 二、根因定位与证据

### 2.1 网易云：接口没坏，客户端把响应丢了（已确证）

**在线实测（2026-11-09 01:0x，本机直连，`dart run tool/check_netease_qr.dart`）**：

```
=== 1) NeteaseApi.createQrLogin() ===
[JXMusic][网易云登录] 取码 HTTP=200 code=200 unikey=d3a9…f8b3(len=36)
[create] qrUrl=https://music.163.com/login?codekey=d3a9…(len=36) key=d3a9…(len=36) lastError=-
=== 2) NeteaseApi.pollQrLogin()（无人扫码，应保持等待态）===
[JXMusic][网易云登录] 轮询 HTTP=200 code=801 message=等待扫码
[poll1] session=null(等待) lastError=-
...（poll2/poll3 同）
=== 3) 原始 client/login 响应（证明端点可达与 code 语义）===
[raw] HTTP=200 body={"code":801,"message":"等待扫码"} set-cookie-names=[NMTID]
结果：PASS（取码成功、轮询为 801 等待态、client/login 端点可达）
```

独立第二次探测（PowerShell `Invoke-WebRequest`，与 Dart 实现无关）：

```
POST https://music.163.com/api/login/qrcode/unikey        → 200 {"code":200,"unikey":"40bb…"}
POST https://music.163.com/api/login/qrcode/client/login  → 200 {"code":801,"message":"等待扫码"}
```

结论：`unikey` 与 `client/login` 端点均可用，**"扫码确认后无反应"不是接口下线**。旧代码的 4 个具体缺陷（`lib/services/api/netease_api.dart` 修改前 365-394 行）：

1. **强转**：`final code = resp.data['code'] as int?;` —— 服务端若返回字符串 `"803"`，Dart 抛 `TypeError`，被设置页 `_poll` 的 `catch (_) {}` 吞掉，表现为"永远等待"。
2. **静默**：`pollQrLogin` 无 try/catch、`lastError` 恒为 null，任何网络/解析异常都不可见。
3. **803 只读响应体**：`resp.data['cookie'] ?? resp.data['token']`；但本轮实测等待态 801 的 Set-Cookie 只有 `NMTID`，官方 2026 文档（MiniPlayer `API_ANALYSIS.md` 2026-04：803 从 **Set-Cookie** 提取 MUSIC_U）与独立实现（Live-streaming `test_netease_qr_login.py`：803 响应体只有 `{code, message}`，`MUSIC_U` 在响应头）都指向同一结论：**旧代码即使拿到 803 也只能得到空 cookie 会话** → 对应现象 C（"提示成功但实际未登录/重启掉线"）。
4. **状态码无语义**：800（过期）/802（待确认）与 801（等待）同样返回 null，过期后也永远等待。

### 2.2 QQ：**同名空 Set-Cookie 覆盖有效 p_skey**（2026-11-09 18:53:59 实扫定案）

**实扫原始 Set-Cookie 证据**（check_sig#1 的 302 响应，用户昵称 ゞ李先森）：

```
pt2gguin=(空) | pt2gguin=o093…4248(len=11) | p_uin=o093…4248(len=11)
| pt4_token=3FTq…U70_(len=44) | p_skey_forbid=(空) | p_skey=q2Dv…pVM_(len=44)
| pt_oauth_token=oasF…l58_(len=76) | p_uin=(空) | p_skey=(空) | pt4_token=(空)
| pt_login_type=len=1
```

→ 服务端**先下发有效 `p_skey`（44 字符），随后又下发同名清空行 `p_skey=`**（用于删除父域/其它 Path 上的旧 cookie）。
旧 `_collectSetCookies` 是 **last-wins**，被空值覆盖 → jar 里 `p_skey` 为空 → authorize 的 `g_tk = hash33('') = 5381` → 302 到登录页拿不到 code；OAuth 链同样依赖 p_skey，因此也拿不到 code。**问题在 cookie 合并逻辑，不在协议参数**。

**修复**：`_collectSetCookies` 忽略值为空的 Set-Cookie（qq_api / netease_api 一致），并加离线单测：模拟「有效 p_skey + 同名空行」断言 `jar['p_skey']` 仍为有效值、authorize 的 `g_tk` 等于 `hash33(有效p_skey,5381)` 且不为 5381。

（历史排查记录：曾比对参考实现 `L-1124/QQMusicApi::_authorize_qq_qr` 的 18 个 check_sig 参数，与旧实现逐字段一致；因此排除了参数集差异，最终由原始 Set-Cookie 行定位到合并逻辑。）

### 2.3 现象 C（登录成功但未登录 / 重启掉线）

- 网易云：2.1 第 3 点已确证（空 cookie 会话）。新代码在 803 时同时收集**响应体 cookie**与**响应头 Set-Cookie**，并要求 `MUSIC_U`（或 `MUSIC_A`）存在，缺失时**不返回会话**而是写 `lastError`。
- Hive 持久化链路本身（`lib/providers.dart` 33-68 行：`musicHubProvider` 构造时 `restoreSession(_loadAccount(...))`；`AccountNotifier.login` 写 Hive；`settings_page._showQrLogin` 写 Hive + 同步客户端）静态检查未见问题；本轮在设置页加了"登录态已写入"日志（`settings_page.dart:385`），实扫成功后会打印 `platform/nickname/cookies 数量`，再重启 App 复核是否仍显示已登录（**已实扫复核通过**，见 5.4）。
